# UX audit — 2026-08-16 (unattended session)

First systematic pass over the **live, human-facing surface** of the browser build. This is
the part of the project nothing automated has ever touched: the 30 replay traces, pixel
hashes and smoke tests all run through `validate` mode or scripted input, so menus, pause,
save/load and input edge cases have only ever been checked by hand, if at all.

Testing was done headlessly via the new `scripts/ux_probe.mjs` (no browser window, no audio),
so everything below is reproducible with a committed scenario file rather than a description
of what someone once clicked.

## Resolved during the session

**Finding #1 (Kid not drawn after quickload) is faithful C behavior, not a port bug.**

Established by driving the C oracle and the Rust build through the *same* scripted
quicksave/quickload scenario and diffing: **100/100 frames, zero state divergence, byte-identical
pixel hashes.** The C original does not draw the Kid after a quickload either. Per the
no-behavior-changes directive this must be left exactly as it is.

Two things had to be true to get that answer, and both were initially wrong:

- **The scripted-input clock is `state_dump::next_tick()`** (`seg009.rs:4672`), which only
  advances inside `play_level_2`'s loop. Before the first level starts it is frozen at 0, so
  any event scheduled at tick > 0 never fires — the game sits on the title splash forever and
  never reaches the code that writes traces. This is why "native interactive mode writes no
  trace" looked like a missing feature; it is not. Launch straight into a level
  (`prince headless megahit 3`, as `scripts/gameplay_smoke_test.sh` does) and both scripted
  input and tracing work fine. **Scripted input cannot drive the title/intro screens** — that
  is the real limitation, and it is narrower than it first appeared.
- **Interactive runs must have the RNG seed pinned.** Without `seed=<n>` the seed comes from
  the clock, and two runs of the same build diverge at frame 1. The first C-vs-Rust comparison
  looked like a real divergence and was pure noise; with the seed pinned they are identical.

The upshot is a genuinely new capability: **the live, human-facing surface is differentially
testable against the C oracle**, using a scripted input file plus `seed=` — the same guarantee
replays already give the simulation. This is a better outcome than the "blocked, needs new
infrastructure" conclusion it replaced.

Remaining real gap: the C oracle has no `dump_frame_raw` (`POPRAWFRAME_*`), so raw frames can
only be captured from the Rust build. Pixel *hashes* compare fine across both, which is enough
for pass/fail; the raw dump is only needed for eyeballing *how* a frame differs.

## Non-findings (checked, working as intended)

- **`Ctrl+G` appeared to do nothing** — correct: save game is only available on levels 3–13
  (`README.upstream.md:204`), and the test was on level 1. Nearly logged as a bug.
- **`PRINCE.SAV` / `PRINCE.HOF` are 0 bytes in OPFS** — empty placeholders created by the
  persistence layer, not evidence of failed writes.

## Later in the session

Everything above was written before the C-oracle comparison existed. What followed:

- **A green test that tested nothing.** `restart_level.txt` (Ctrl+A) passed the live-surface
  diff on its first run — because *both* builds hardcoded `keysym.mod = 0` on injected
  scripted-input events and ignored the modifier identically. They agreed perfectly while
  doing nothing. Only checking the intended effect (Kid.x resetting to the level start)
  exposed it. Fixed in both builds. **A differential test cannot catch a bug both sides
  share.**
- **`POPTRACE_NOWAIT`** lets scripted runs skip the frame-timer pacing (~12 ticks/sec →
  uncapped), taking the live-diff suite from ~90s to 4s. The first attempt at this was wrong:
  returning early from the wait functions also skipped `update_screen()` and `process_events()`,
  which moved when scripted input is injected and shifted the Kid's frame by one tick. I had
  justified it with "timing doesn't feed the simulation", which was too glib — the byte
  comparison caught it. Now verified C real-time ≡ C no-wait ≡ Rust no-wait, exactly.
- **CI proven to fail**, not just pass: a throwaway branch with a deliberately failing test
  went red for that exact test, then was deleted.
- **A game-beater substrate** (`scripts/beat_level.py`) built on this infrastructure. Works end
  to end, makes real progress (level 2: 8 → 18 tiles explored), does not beat a level yet.
- **Level 1 ignores scripted input entirely** (Kid starts crouched); levels 2–5 respond. Not a
  port bug — C and Rust are identical over 150 ticks.

## Assumptions made

1. **Mapped only the keys the game actually binds**, not all of A–Z, so unmapped keys fall
   through without `preventDefault` and browser shortcuts the game doesn't use (Ctrl+W/T/N)
   keep working. The alternative — mapping everything — would hijack them.
2. **Left the existing F1–F12 mappings alone**, including F5 and F11, even though the game
   only binds F6/F9/F12. Narrowing them would restore browser reload / fullscreen but changes
   behavior that predates this session.
3. **Did not push.** CI is committed but has never run; it cannot be verified without a push,
   and `origin` is behind local `master`.
4. **Stopped investigating finding #1** rather than guessing at a fix, on the grounds that a
   wrong "fix" to faithful behavior is worse than an open ticket.
